## 1. How to read this dictionary

- **Logical type** is a platform-independent domain (`identifier`, `text`, `code`, `date`, `timestamp`, `decimal`). Oracle types and sizes belong to Phase IV and are deliberately not specified here.
- **Required** means the column must not be `NULL`. **Optional** means the source can be blank and the column must allow `NULL`.
- **Unique** means the column or column combination has a unique constraint. `PK` is the primary key; `UK` is a natural unique key.
- A blank CSV cell maps to `NULL`, never to zero.
- All monetary amounts are in Kenyan Shillings (KES). All timestamps are recorded in UTC+3 (East Africa Time).
- Surrogate keys (`rider_id`, `unit_id`, `daily_id`, `trip_id`, `maintenance_event_id`, `audit_id`) are logical identifiers. Phase IV will choose sequences or identity columns.
- The dataset contains no names, phone numbers, e-mail addresses or registration plates. `source_user_id` is a pseudonymous numeric-looking identifier and is kept as text so the source value is preserved exactly.

## 3. Table definitions

### 3.1 `RIDER`

**Purpose:** Stores one row per distinct anonymised rider. A rider is the person behind a `user_id`; the same rider can participate in more than one study cohort.  
**Source:** `user_id` from all six CSV files.  
**Grain:** One row per distinct `user_id`.

| Column | Logical type | Required | Unique | Source / derivation | Description |
|---|---|---|---|---|---|
| `rider_id` | identifier | Yes | PK | Surrogate | Unique rider identifier used by the logical model |
| `source_user_id` | text | Yes | UK | `user_id` | Pseudonymous rider identifier exactly as supplied in the CSV. Kept as text to preserve the source value and any leading characters |

**Keys and constraints**

- `PK (rider_id)`
- `UK (source_user_id)`
- No foreign keys.

**Business rules**

- 119 rows are expected.
- `source_user_id` is not unique across cohorts but is unique in this table because a rider exists once.
- No personal data is stored beyond the pseudonymous source identifier.

---

### 3.2 `COHORT`

**Purpose:** Stores the three study groups and their phase/powertrain descriptors, so those descriptors are not repeated on every daily or trip row.  
**Source:** Derived from the six source file names; there is no cohort column in the CSV.  
**Grain:** One row per cohort.

| Column | Logical type | Required | Unique | Source / derivation | Description |
|---|---|---|---|---|---|
| `cohort_name` | code | Yes | PK | File name | Study group code: `BASELINE`, `CONTROL` or `TREATMENT` |
| `study_phase` | code | Yes | No | File name | Phase code: `BASELINE` or `TRANSITION` |
| `powertrain_type` | code | Yes | No | File name | Powertrain code: `FUEL` or `ELECTRIC` |

**Keys and constraints**

- `PK (cohort_name)`
- No foreign keys.

**Business rules**

- Exactly three rows:

| `cohort_name` | `study_phase` | `powertrain_type` | Source files |
|---|---|---|---|
| `BASELINE` | `BASELINE` | `FUEL` | `baseline-fuel-motorcycle-*` |
| `CONTROL` | `TRANSITION` | `FUEL` | `transition-control-fuel-motorcycle-*` |
| `TREATMENT` | `TRANSITION` | `ELECTRIC` | `transition-treatment-electric-motorcycle-*` |

- `powertrain_type` and `study_phase` depend on `cohort_name`; this is why they live here rather than in `RIDER_UNIT` or the child tables.

---

### 3.3 `RIDER_UNIT`

**Purpose:** Resolves the many-to-many relationship between riders and cohorts. It is the tracked unit: one rider participating in one cohort. Daily rows, trips and maintenance events belong to a unit.  
**Source:** Distinct (`user_id`, cohort) pairs; the cohort comes from the file name.  
**Grain:** One row per rider-cohort pair.

| Column | Logical type | Required | Unique | Source / derivation | Description |
|---|---|---|---|---|---|
| `unit_id` | identifier | Yes | PK | Surrogate | Unique tracked-unit identifier |
| `rider_id` | identifier | Yes | UK part | `RIDER.rider_id` | The rider who participates |
| `cohort_name` | code | Yes | UK part | `COHORT.cohort_name` | The cohort the rider participates in |

**Keys and constraints**

- `PK (unit_id)`
- `UK (rider_id, cohort_name)`
- `FK (rider_id) → RIDER (rider_id)`
- `FK (cohort_name) → COHORT (cohort_name)`

**Business rules**

- 235 rows are expected (118 baseline + 108 control + 9 treatment rider-cohort pairs). The 119 riders split as 9 riders in 3 cohorts, 98 riders in 2 cohorts and 12 riders in 1 cohort: 9×3 + 98×2 + 12×1 = 235.
- A unit is identified by (`rider_id`, `cohort_name`), never by `source_user_id` alone.
- 107 of 119 riders appear in more than one cohort; all 9 electric riders also appear in the control and baseline cohorts. This is valid many-to-many participation, not a duplicate.
- `powertrain_type` and `study_phase` are **not** stored here; they are reached through `COHORT` to avoid a transitive dependency.

---

### 3.4 `DAILY_OPERATIONS`

**Purpose:** Stores one aggregated operating day for one tracked unit: distance, travel time, idle time, revenue and the daily maintenance total.  
**Source:** The three daily CSV files (`baseline`, `transition-control`, `transition-treatment`).  
**Grain:** One row per unit per operating date.

| Column | Logical type | Required | Unique | Source / derivation | Description |
|---|---|---|---|---|---|
| `daily_id` | identifier | Yes | PK | Surrogate | Unique daily-operation identifier |
| `unit_id` | identifier | Yes | UK part | `RIDER_UNIT.unit_id` | The tracked unit that operated |
| `operating_date` | date | Yes | UK part | `date` | Calendar date of the daily summary |
| `distance_km` | decimal | Yes | No | `distance_km` | Total distance travelled that day, in kilometres. Source has 0 missing values |
| `duration_min` | decimal | Yes | No | `duration_min` | Total travel time that day, including idle time, in minutes. Source has 0 missing values |
| `idle_time_min` | decimal | Yes | No | `idle_time_min` | Total time spent on momentary stops (under one minute) that day, in minutes. Source has 0 missing values |
| `revenue_kes` | decimal | Optional | No | `revenue_kes` | Revenue earned that day, in KES. 266 baseline, 209 control and 4 electric rows are blank |
| `maintenance_kes` | decimal | Optional | No | `maintenance_kes` | Daily maintenance total, in KES. This is an aggregate, not an event. 266 baseline, 209 control and 4 electric rows are blank |

**Keys and constraints**

- `PK (daily_id)`
- `UK (unit_id, operating_date)`
- `FK (unit_id) → RIDER_UNIT (unit_id)`

**Business rules**

- 2,718 rows are expected (1,480 baseline + 1,150 control + 88 electric).
- The unique key prevents two daily summaries for the same unit and date.
- The same `source_user_id` on the same date in two cohorts produces **two different units**, so both rows are valid. There are 88 such control/electric pairs.
- Missing coverage is represented by an **absent row**, not by a NULL measure: 172 baseline unit-days, 146 control unit-days and 20 electric unit-days are absent.
- `distance_km`, `duration_min`, `idle_time_min`, `revenue_kes` and `maintenance_kes` must be greater than or equal to zero when present.
- The source contains revenue, maintenance, duration and idle-time outliers. They are retained and flagged for review; they are not silently corrected or deleted.
- `maintenance_kes` must not be copied into `MAINTENANCE_EVENTS`; doing so would double count the same cost.

---

### 3.5 `FUEL_DAILY_COSTS`

**Purpose:** Stores the fuel-cost detail for a fuel unit-day. It is a one-to-one child of `DAILY_OPERATIONS`, present only for fuel units.  
**Source:** Baseline and control daily CSVs.  
**Grain:** One row per fuel daily operation.

| Column | Logical type | Required | Unique | Source / derivation | Description |
|---|---|---|---|---|---|
| `daily_id` | identifier | Yes | PK, FK | `DAILY_OPERATIONS.daily_id` | The fuel daily operation this cost belongs to |
| `fuel_cost_kes` | decimal | Optional | No | `fuel_cost_kes` | Daily fuel cost, in KES. Blank in 266 baseline and 209 control rows |
| `fuel_unit_cost_kes_per_l` | decimal | Optional | No | `fuel_unit_cost_kes_per_l` | Fuel unit price, in KES per litre. Where present it is 214.30 in baseline and 217.36 in control |
| `fuel_amount_l` | decimal | Optional | No | `fuel_amount_l` | Fuel consumed that day, in litres |

**Keys and constraints**

- `PK (daily_id)`
- `FK (daily_id) → DAILY_OPERATIONS (daily_id)`

**Business rules**

- 2,630 rows are expected (1,480 baseline + 1,150 control).
- One row exists for every fuel daily operation, even when all three cost values are `NULL`; this preserves the one-to-one link. The 475 all-blank rows (266 baseline + 209 control) are valid rows with `NULL` values.
- All numeric values must be greater than or equal to zero when present.
- The constant unit prices are data characteristics, not a reason to remove the column.

---

### 3.6 `ELECTRIC_DAILY_COSTS`

**Purpose:** Stores the electric-cost detail for an electric unit-day. It is a one-to-one child of `DAILY_OPERATIONS`, present only for electric units.  
**Source:** Treatment (electric) daily CSV.  
**Grain:** One row per electric daily operation.

| Column | Logical type | Required | Unique | Source / derivation | Description |
|---|---|---|---|---|---|
| `daily_id` | identifier | Yes | PK, FK | `DAILY_OPERATIONS.daily_id` | The electric daily operation this cost belongs to |
| `battery_swap_cost_kes` | decimal | Optional | No | `battery_swap_cost_kes` | Daily battery-swap cost, in KES. Blank in 48 of 88 rows |
| `kwh_charging` | decimal | Optional | No | `kwh_charging` | Energy charged that day, in kWh. Blank in 60 of 88 rows |

**Keys and constraints**

- `PK (daily_id)`
- `FK (daily_id) → DAILY_OPERATIONS (daily_id)`

**Business rules**

- 88 rows are expected, one per electric daily row.
- All numeric values must be greater than or equal to zero when present.
- Battery-swap cost and kWh are independently missing; a row may have one, both or neither.

### 3.7 `TRIPS`

**Purpose:** Stores one GPS-tracked trip for one tracked unit. This is the child that removes the repeating group of trips from a unit-day.  
**Source:** The three trip CSV files.  
**Grain:** One row per trip.

| Column | Logical type | Required | Unique | Source / derivation | Description |
|---|---|---|---|---|---|
| `trip_id` | identifier | Yes | PK | Surrogate | Unique trip identifier |
| `unit_id` | identifier | Yes | UK part | `RIDER_UNIT.unit_id` | The unit that made the trip |
| `start_ts` | timestamp | Yes | UK part | `start_date` + `start_time` | Trip start date and time as one timestamp |
| `end_ts` | timestamp | Yes | UK part | `end_date` + `end_time` | Trip end date and time as one timestamp |
| `duration_min` | decimal | Yes | No | `duration_min` | Total trip duration, in minutes. Source has 0 missing values |
| `distance_km` | decimal | Yes | UK part | `distance_km` | Recorded trip distance, in kilometres. Source has 0 missing values |
| `idle_time_min` | decimal | Yes | No | `idle_time_min` | Time during the trip spent on momentary stops (under one minute), in minutes. Source has 0 missing values |
| `start_lat` | decimal | Optional | No | `start_lat` | Start latitude in decimal degrees. 1,480 baseline, 1,150 control and 88 electric values are blank |
| `start_lon` | decimal | Optional | No | `start_lon` | Start longitude in decimal degrees. Same missing pattern as `start_lat` |
| `end_lat` | decimal | Optional | No | `end_lat` | End latitude in decimal degrees. Same missing pattern as `start_lat` |
| `end_lon` | decimal | Optional | No | `end_lon` | End longitude in decimal degrees. Same missing pattern as `start_lat` |
| `avg_speed_kmh` | decimal | Yes | No | `avg_speed_kmh` | Average speed including idle time, in km/h. Source has 0 missing values |
| `avg_moving_speed_kmh` | decimal | Yes | No | `avg_moving_speed_kmh` | Average speed considering movement only, in km/h. Source has 0 missing values |
| `max_speed_kmh` | decimal | Yes | No | `max_speed_kmh` | Maximum speed over a 10-second sampling interval, in km/h. Source has 0 missing values |

**Keys and constraints**

- `PK (trip_id)`
- `UK (unit_id, start_ts, end_ts, distance_km)`
- `FK (unit_id) → RIDER_UNIT (unit_id)`

**Business rules**

- 126,067 rows are expected (68,325 baseline + 54,087 control + 3,655 electric).
- The unique key is scoped to the unit. The 3,655 electric trips that repeat control trips on all 15 source fields are **not duplicates** in this design because they belong to different units.
- Coordinates are optional by design: the publisher removed first and last trip coordinates for privacy. 2,954 baseline, 2,288 control and 174 electric trips have at least one missing coordinate.
- `end_ts` must be greater than or equal to `start_ts`.
- `duration_min`, `distance_km`, `idle_time_min`, `avg_speed_kmh`, `avg_moving_speed_kmh` and `max_speed_kmh` must be greater than or equal to zero when present.
- Latitude must be between -90 and 90; longitude must be between -180 and 180. There are 0 out-of-range coordinates in the source.
- Known source anomalies are retained for review: 307 trips where `max_speed_kmh` is below `avg_speed_kmh`; 19 trips with an average or moving-average speed above 100 km/h (11 baseline values above 200 km/h, maximum 2,004.29 km/h); 97 zero-distance trips; 1 trip whose duration differs from its timestamps by more than one minute; 55 cross-midnight trips.
- There is no per-trip revenue or fare in the source. `TRIPS` does not invent one.
- There is no `daily_id` foreign key in `TRIPS`, because the daily file is a separate aggregate and may not reconcile exactly with the trip rows.

---

### 3.8 `MAINTENANCE_EVENTS`

**Purpose:** Stores event-level maintenance for a tracked unit. It is included so the model can hold individual service events without overloading the daily aggregate.  
**Source:** **No source rows.** The raw data supplies only the daily `maintenance_kes` aggregate.  
**Grain:** One row per maintenance event.

| Column | Logical type | Required | Unique | Source / derivation | Description |
|---|---|---|---|---|---|
| `maintenance_event_id` | identifier | Yes | PK | Surrogate | Unique maintenance-event identifier |
| `unit_id` | identifier | Yes | No | `RIDER_UNIT.unit_id` | The unit that received maintenance |
| `maintenance_date` | date | Yes | No | Future/manual | Date of the maintenance event |
| `maintenance_type` | code | Yes | No | Future/manual | Event type. Proposed values: `PREVENTIVE`, `CORRECTIVE`, `INSPECTION`, `OTHER` |
| `description` | text | Optional | No | Future/manual | Short description of the work performed |
| `amount_kes` | decimal | Yes | No | Future/manual | Cost of the event, in KES. Zero is allowed for warranty or free service |
| `odometer_km` | decimal | Optional | No | Future/manual | Odometer reading at the event, in kilometres |

**Keys and constraints**

- `PK (maintenance_event_id)`
- `FK (unit_id) → RIDER_UNIT (unit_id)`

**Business rules**

- 0 rows are loaded from the raw dataset.
- `amount_kes` must be greater than or equal to zero.
- `odometer_km` must be greater than or equal to zero when present.
- Do not copy `DAILY_OPERATIONS.maintenance_kes` into this table. Either keep the daily aggregate or derive it from events; do not store both as if they were independent facts.

---

### 3.9 `AUDIT_LOG`

**Purpose:** Append-only audit trail for data changes, populated by database triggers.  
**Source:** Generated by DML triggers, not by the CSV files.  
**Grain:** One row per audited change.

| Column | Logical type | Required | Unique | Source / derivation | Description |
|---|---|---|---|---|---|
| `audit_id` | identifier | Yes | PK | Surrogate | Unique audit-record identifier |
| `table_name` | text | Yes | No | Trigger | Name of the table that changed |
| `record_key` | text | Yes | No | Trigger | Primary-key value of the changed row, rendered as text |
| `action_type` | code | Yes | No | Trigger | `INSERT`, `UPDATE` or `DELETE` |
| `changed_by` | text | Yes | No | Trigger / database user | Database user responsible for the change |
| `changed_at` | timestamp | Yes | No | Trigger / current timestamp | Date and time of the change |
| `old_summary` | text | Optional | No | Trigger | Short summary of the old values; `NULL` for `INSERT` |
| `new_summary` | text | Optional | No | Trigger | Short summary of the new values; `NULL` for `DELETE` |

**Keys and constraints**

- `PK (audit_id)`
- No foreign keys. This table is intentionally standalone.

**Business rules**

- Append-only: triggers insert, and no application path updates or deletes audit rows.
- `old_summary` is required for `UPDATE` and `DELETE`; `new_summary` is required for `INSERT` and `UPDATE`.
- Store a summary, not the entire row, to keep the log small and avoid copying sensitive values.
- 0 rows initially.

### 6.2 Derived values not stored as columns

| Derived value | Rule | Reason not stored |
|---|---|---|
| `source_group` (current Phase IV label) | `BASELINE` → `BASELINE_FUEL`; `CONTROL` → `TRANSITION_CONTROL_FUEL`; `TREATMENT` → `TRANSITION_ELECTRIC` | Derivable from `COHORT`; storing it on every child row is redundant |
| Unit identity | (`source_user_id`, `cohort_name`) | Resolved to `unit_id`; the natural pair is enforced by `RIDER_UNIT`'s unique key |
| Fuel/electric applicability | `COHORT.powertrain_type` | Reached through `unit_id → cohort_name` |
| Study phase | `COHORT.study_phase` | Reached through `unit_id → cohort_name` |
| Daily maintenance total vs event total | Keep one or the other; `maintenance_kes` is the daily aggregate | Avoid double counting |

### 6.3 Type conversion rules

| Source form | Logical form | Rule |
|---|---|---|
| Empty CSV cell | `NULL` | `NULLIF(TRIM(value),'')`; never zero |
| Numeric-looking text | decimal | `TO_NUMBER(NULLIF(TRIM(value),''))` |
| `YYYY-MM-DD` text | date | `TO_DATE(value,'YYYY-MM-DD')` |
| `HH:MM:SS` text | time part | Combine with date before conversion |
| Date + time | timestamp | `TO_TIMESTAMP(CONCAT(CONCAT(date,' '),time),'YYYY-MM-DD HH24:MI:SS')` |
| Numeric-looking `user_id` | text | Keep as text; do not convert to a number |
| File name | code values | Map one of six known names to the three cohort rows |
| Currency values | decimal KES | No currency symbol or thousands separator is present; do not rescale |
| Coordinates | signed decimal degrees | Negative latitude is valid for Nairobi (south of the equator) |

## 8. Assumptions and open points for Phase IV

1. **Surrogate key strategy.** The logical design uses numeric-looking identifiers but does not prescribe sequences, identity columns or hashes. Phase IV will decide.
2. **Precision and scale.** Decimal precision for distances, durations, speeds and money is not fixed here. Phase IV will size the Oracle columns.
3. **`source_user_id` type.** It is numeric-looking text. Keeping it as text avoids accidental conversion and preserves the source exactly; Phase IV should keep the same choice.
4. **Cost-row creation.** The logical design expects one `FUEL_DAILY_COSTS` row per fuel daily operation and one `ELECTRIC_DAILY_COSTS` row per electric daily operation, even when all cost values are `NULL`. Phase IV may instead omit all-null cost rows; if so, document the rule.
5. **Daily-to-trip linkage.** No `daily_id` foreign key is placed in `TRIPS` because the daily file has no trip identifier and the aggregates may not reconcile. Phase IV may add a derived link only if it can be validated.
6. **Maintenance.** The source has a daily maintenance aggregate, not events. `MAINTENANCE_EVENTS` remains empty unless event data is collected later. Do not double count.
7. **Phase IV alignment.** The current physical script keeps `source_user_id`, `powertrain_type`, `cohort_name` and `study_phase` in `RIDER_UNITS` and stores `source_group` in child tables. This dictionary follows the 3NF logical design, which extracts `COHORT`, separates `RIDER` from `RIDER_UNIT`, and omits `source_group` from child tables. Either align the physical schema or document the shortcut as a controlled denormalization.
8. **No trip fare.** Revenue exists only at daily level. Do not add a fare column to `TRIPS` without a source.
9. **Time zone.** All timestamps are treated as UTC+3. No conversion is applied.
10. **Raw data is immutable.** All cleaning and conversion happens in staging/load logic, never in `data/raw/`.
